Design conversation captured 2026-04-18 about separating tasks / ideas
/ notes / memories in hopper without forcing users to classify at
capture time.

Core decisions:

1. One capture primitive — `hopper note "..."` — always lands with
   `kind: inbox` (or null). No flags required. "Note" is the verb,
   not the terminal type.

2. Terminal kinds (task / idea / note / memory / reference) are set by
   a triage agent, not by the user. The same item can be re-classified
   later without losing prior edits.

3. Triage runs on demand, not as a daemon. Any agent with context
   (Claude session, server-side agent, local CLI agent) can triage.
   Convergence guaranteed by both agents reading the same versioned
   rubric stored inside hopper itself.

4. Staleness via flag, not bucket: every item carries
   `last_triage` (timestamp) and `taxonomy_version` (int). Triage
   candidates are items where
      last_triage IS NULL
      OR updated_at > last_triage
      OR taxonomy_version < current
   Re-running is always safe and idempotent.

5. Consequence for views: `hopper task list`, `hopper idea list`,
   `hopper memory list` are filtered views over the inbox. They are
   eventually-consistent — a freshly dropped note is invisible to
   lifecycle queries until *some* agent triages it. Acceptable
   tradeoff; mitigated by inline quick-triage on capture if needed.

Open questions:
- Where does the rubric live? Suggest
  `.hopper/knowledge/triage-rubric.md` with explicit versioning.
- How do local and server-side triage agents avoid stepping on
  each other? Likely via last-write-wins on the `last_triage`
  field (already how sync works).
- What's the schema migration story when we add a new kind?
  Taxonomy_version bump forces re-triage of everything, which is
  fine but needs to be explicit.
- This task itself was captured as a 'task' only because the
  'note' primitive doesn't exist yet. Canonical bootstrap
  problem: the first kind to ship should be 'inbox'.
